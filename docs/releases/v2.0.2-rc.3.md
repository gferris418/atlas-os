# ATLAS OS v2.0.2-rc.3 Candidate Decision

## Decision

Prepare `v2.0.2-rc.3` as the next candidate after published predecessor `v2.0.2-rc.2` at merge commit `7c263b6bdf18f72db2a56d467ce16ca6a5b0b6e4`.

## Scope

This candidate adds a mandatory pre-routing disclosure boundary. Before ATLAS routes any selected function, skill, plugin, tool, model, subagent, or specialist method, it shows what it proposes to do and how: the exact work unit, semantic requirements, provider purpose and method, permission, data scope, prerequisites, fallback, unresolved gates, and execution sequence.

The reference runtime applies the same boundary to non-research providers. For example, a Codex repository-engineering request previews Local Execution before Repository Engineering, discloses their prerequisites and unresolved gates, and remains blocked until the exact proposal digest is approved.

AI hosts can pass explicit semantic `capability_requirements` and an admitted `provider_inventory` through the public execution envelope. This brings native functions, plugins, models, subagents, skills, tools, capabilities, and specialist methods under the same digest-bound gate; an unmatched requirement fails closed.

After taxonomy routing, a lightweight domain-neutral intent profile distinguishes opportunity identification, supplier/vendor sourcing, market validation, general research, and general tasks. It recommends semantic capability needs but cannot select or invoke a provider. Behavioral learning is disabled by default and remains explicit host-managed preference state rather than hidden core policy.

Approval is bound to the proposal's SHA-256 digest. Rejection, omission, a stale digest, or any changed proposal blocks routing. Routing decisions are returned as a receipt. ARGUS remains subordinate to ATLAS and cannot activate merely because its preview was approved; its immutable Domain Context Handoff must still be acceptable.

ChatGPT and Hermes Agent use the same provider-neutral control revision, `atlas-bootstrap-2026-10-21-r7`.

## Verification requirements

Candidate packaging requires dependency audit, unit, conformance, regression, integration, repository-validation, deterministic-package, protected-branch, and CodeQL checks. Live ChatGPT and Hermes Agent proof must separately demonstrate that provider invocation never precedes the exact routing preview and approval.

## Stable-release blockers

Stable `v2.0.2` remains blocked by:

- `MIG-029`, requiring independent fresh-session ChatGPT New Chat and ChatGPT Work proof for revision `r7`; and
- `MIG-037`, requiring independent latest-control propagation proof across supported surfaces, including Hermes Agent.

## Publication rule

`v2.0.2-rc.3` may be tagged only on the exact validated merge commit. The tag-triggered release workflow must verify tag/manifest identity and rebuild deterministic artifacts. Candidate preparation does not authorize publication and does not imply stable release or completion of `MIG-029` or `MIG-037`.
